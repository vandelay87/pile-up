# Prototype v2 spec: power, and the corpse loop reworked

This spec gathers every technical decision for prototype v2 in one place and ends in the ordered list of build tickets. v2 adds power (the power grid, pylons and the repair yard) and reworks v1's corpse loop after playtesting: the map is narrow, the pace is fast, every structure can be attacked, and bodies land where enemies die.

It is self-contained: where v2 keeps a v1 rule, the rule is restated here, and `docs/specs/v1.md` stays frozen as history. Game rules and their starting numbers come from `docs/design.md`; vocabulary from `GLOSSARY.md`. If this spec and a closed ticket disagree, this spec is current. Planned in [Map: prototype v2 spec](https://github.com/vandelay87/pile-up/issues/47).

## 1. Platform and engine

Unchanged from v1.

- Godot 4.7.2, standard build, typed GDScript, pinned in one CI workflow variable.
- Platforms: macOS and Windows. Baseline machine: Apple M5 MacBook, 16 GB RAM.
- Performance target: about 1,000 enemies on screen at 60 fps on the baseline machine.
- No C#. A hot loop that has to leave GDScript moves to a C++ GDExtension behind the same module interface (ADR 0001).

## 2. Architecture

Sources: ADR 0001, ADR 0002, [Code organisation and system boundaries](https://github.com/vandelay87/pile-up/issues/11).

The v1 architecture stands: a node-free `Simulation` owns every system, their seeded RNGs and the tick driver; the view draws it and turns input into commands; nothing under `src/sim/` extends `Node` or `Resource` or references `src/view/`, and the `lint` job enforces it. Commands drain at step 0, so a seed plus a list of (tick, command) pairs replays a run exactly. Systems never signal each other; the tick driver passes data between them. A restart builds a fresh `Simulation`.

### What changes in v2

- **Leaks are retired** (ADR 0001's amendment already turned the `leaked` signal into a list; v2 removes it). The enemy removal step returns deaths only. Enemies reaching the base attack it instead.
- **Lives become base HP.** `RunState` holds base HP; the run ends when it reaches 0.
- **Towers grow into `Buildings`.** One system owns every building (towers, pylons and repair yards) with a stable id, kind, origin, footprint, HP and powered flag, in build order. Tower firing and drone behaviour read it.
- **New systems:** `PowerGrid` (which buildings are powered and which cells are on the grid) and `RepairYards` (drones). The combo lives in `RunState`.
- **One structure interface.** Enemies attack walls, buildings and the base through one `Structures` facade that looks a cell up and routes damage to `Piles`, `Buildings` or `RunState`. It owns no state of its own.

### Systems

| System | Owns | Interface (main parts) |
|---|---|---|
| `MapData` | Immutable loaded map | `is_rock(cell)`, `is_base(cell)`, `spawn_cells(edge)` |
| `Occupancy` | Building id per cell | written by `Buildings` on build and destruction |
| `Piles` | Level and wall HP per cell; landing and decay | `queue_bodies(positions)`, `damage_wall(cell, amount)`, `decay(rng)`; change list for `Routing` |
| `Routing` | Both flow fields | incremental update from a change list, `start_rebuild()`, `sample_direction(route, pos)`, `sample_value(route, pos)` |
| `Enemies` | Packed enemy arrays and the spatial hash | `spawn(cell_pos)`, `damage(id, amount)`, `nearest_to_base_in_range(pos, range)`; removal step returns the death list |
| `Structures` | Nothing (a facade) | `structure_at(cell)`, `damage(cell, amount)`, `hp(cell)`, `bucketed_hp(cell)` |
| `Buildings` | Every building in build order | `can_place(kind, origin)`, `build(kind, origin)`, `damage(id, amount)`, `building(id)`; tower firing builds the per-tick shot list |
| `PowerGrid` | Powered flag per building, the grid's cell set | `recompute(buildings)`, `is_on_grid(cell)`, `is_powered(id)` |
| `RepairYards` | One drone per yard: state, position, target, assignment | `assign(yard_id, building_id)`, `clear(yard_id)`, `step()` |
| `Waves` | Spawn schedule, edges, clump bursts, Enemies left, wave tail, phase | `enemies_left()`, `in_wave_tail()` |
| `RunState` | Gold, base HP, wave number, Kills, the combo, game over | `can_afford(cost)`, `record_kills(n, tick)`, `damage_base(amount)` |

### Commands (new and changed)

- `Build(kind, origin)` replaces `BuildTower`, for `tower`, `pylon` and `repair_yard`.
- `Assign(yard_id, building_id)` and `ClearAssignment(yard_id)`.
- Selecting a building is view-only: it is not a command and does not change the simulation.

### Signals out to the view (end of tick)

`pile_changed`, `fields_changed`, `gold_changed`, `base_hp_changed(hp)`, `building_placed(id)`, `building_destroyed(id)`, `power_changed`, `shots_fired(shots)`, `kills_changed(kills)`, `enemies_left_changed(n)`, `combo_changed(tier)`, `payout(amount, tier)`, `phase_changed`, `wave_started(edges)`, `command_rejected(reason)`, `game_over`. `lives_changed` and `tower_placed` are removed.

Building HP, drone positions and repair state change every tick, so the view and the selection panel read them read-only each frame, as the enemy renderer reads the enemy arrays.

## 3. Tick order

The v1 order, with three new jobs: power is recomputed whenever the set of buildings changes, structures take damage during movement, and drones fly at a new step after towers fire.

0. Drain commands (builds, assignments, next wave, restart, settings, debug actions). A successful build recomputes power at once, so a new tower can fire on the tick it is built.
1. `Piles` lands bodies queued last tick. On the tick after a wave end, `Piles.decay()` and `Routing.start_rebuild()` run next. `Routing` applies the change list (pile level changes, buildings built or destroyed, structure HP bucket changes, walls broken) as an incremental update, and swaps in the decay rebuild once it is due.
2. `Waves` spawns, in clump bursts.
3. Rebuild the spatial hash.
4. Move enemies: flow field, wander and pace, pile slow, separation and personal space, collision, route rolls and wave-tail push-through, structure attacks. Damage applies at once. A building reaching 0 HP is destroyed at once: its cells are cleared in `Occupancy`, its cells join the change list for the next tick, and power is recomputed. Base HP reaching 0 sets game over.
5. Towers target and damage. Only powered towers fire.
6. Drones fly and repair (`RepairYards.step()`).
7. Remove dead enemies. Deaths go to `Piles.queue_bodies`; the kill count goes to `RunState`, which updates Kills and the combo and pays each kill.
8. `Waves` checks for wave end; on wave end, decay becomes due at step 1 of the next tick, drones fly home, and the phase becomes build phase.

Then the end-of-tick signals are emitted. Removal waits until step 7, so enemy ids and indices are stable for the whole tick. Destroyed buildings leave `Buildings` at once, so towers and drones look buildings up by id and treat a missing id as destroyed.

## 4. Settings

Unchanged mechanism from v1 (one schema table in `src/sim/settings.gd`, values in `data/settings/defaults.json`, strict validation, `live` and `restart` settings, step-0 change commands). |---|---|
| `enemies` | speed 2 cells/s, hp 10, bounty 1, structure damage 2 HP/s (renamed from `wall_damage`), speed variety ±3%, wander ±30° over 4 s, personal space radius 0.7 cells and push 0.06, heading offset 10°, roll chances 5% (pile) and 3% (wall or building), turn-back angle 90° |
| `piles` | slows 15/30/45/60%, wall HP 15, decay chance 50% (levels 1–4) and 25% (walls) |

## 5. Map and grid

- **The v2 map** is `data/maps/v2-narrow.json`, taken unchanged from commit bd02607 on `prototype/narrow-map`, and `map_path` defaults to it. `v1.json` stays in the repo as a valid map.
  - 96×64 cells, rock everywhere except the routes and the clearing.
  - Spawn edges N, E and W, each a 13-cell mouth narrowing to a corridor about 7 cells wide.
  - West and east routes run along the top, then S-bend down to a junction on each side. The north route splits around a rock island and feeds both junctions. One corridor runs from each junction into the clearing.
  - A 4×4 base at (46, 46) in a roughly 20×20 clearing, a little smaller than the base's 24×24 starting power area, so the grid just reaches the corridor ends.
- The map's generator script stays on the prototype branch; the map is data.

## 6. Structures

Sources: [Attackable structures: towers and the base](https://github.com/vandelay87/pile-up/issues/50).

- **One rule.** Walls, buildings and the base are structures. An enemy attacks one only when it is in the way: its route crosses it within 2 steps and it is pressed against it (within `separation_radius + wall_reach` of a structure cell's square), or it is jammed against it (no progress along its route field for `jam_seconds` while pressed against it). An enemy passing a structure that is not in its way ignores it.
- **Damage:** every attacker deals 2 HP/s to the structure cell it attacks, through `Structures.damage`. No limit on attackers beyond space. An attacker finishes its target until it falls or the attacker is pushed out of reach, and attackers hold their ground against the crowd behind them (v1 wall rules, now for every structure).
- **Walls:** 15 HP; at 0 HP a wall drops to a level-3 pile (section 9).
- **Buildings:** a tower 60 HP, a pylon 20, a repair yard 60. At 0 HP a building is destroyed and leaves nothing behind: its cells are clear and its gold is lost. Attackers on it go back to walking.
- **The base:** 200 HP in `RunState`. Its cells stay the zero-cost goal of both fields, but no enemy enters them: collision pushes enemies out of base cells like any structure, and an enemy pressed against the base attacks it. Towers keep shooting enemies at the base. At 0 HP the run ends.
- **Bodies at structures:** an enemy killed at a structure dies in front of it, and its body lands by the normal rule (section 9), so defending a structure builds a pile in front of it.

## 7. Routing

Sources: [Flow field design](https://github.com/vandelay87/pile-up/issues/9), [Crowd behaviour at walls](https://github.com/vandelay87/pile-up/issues/14), [Attackable structures](https://github.com/vandelay87/pile-up/issues/50), [Re-routing over long distances](https://github.com/vandelay87/pile-up/issues/59).

### Fields

Two integration fields, **sensible** and **direct**, with each cell's true shortest-path parent, seeded from the base cells, using octile steps with no corner cutting and the fixed tie order E, W, S, N, SE, SW, NE, NW. Walls and buildings count as not walkable for corner cutting.

### Costs

Cost to enter a cell = `step × terrain factor`.

| Cell | Terrain factor |
|---|---|
| Clear | 1 |
| Pile at level L (1–4) | `1 + pile_weight × (1/(1 − slow(L)) − 1)` |
| Wall or building | `1 + wall_weight × break_time_in_cells` |
| Rock | infinite |

- `break_time_in_cells` = remaining HP ÷ structure damage per second × enemy speed, with HP in buckets of `wall_hp_bucket`. A fresh 60 HP tower at 2 HP/s and 2 cells/s is 60 cells; a fresh 15 HP wall is 15. Each bucket change queues one field update.
- Weights: sensible `pile_weight = 1`, `wall_weight = 1`; direct `pile_weight = 0`, `wall_weight = 0.1`.
- **No blocking check.** Every structure has a finite cost, so `would_block` is removed. Boxing the base in is legal: enemies break through the cheapest point.

### When the fields change

As in v1: a synchronous full rebuild on map load and on a route-weight setting change; incremental updates at step 1, batched per tick, for pile level changes, buildings built or destroyed, HP bucket changes and walls broken; a full rebuild on a worker thread after decay, swapped in a fixed 12 ticks later, with "next wave" disabled until the swap. The incremental update must equal a full rebuild exactly.

### Route rolls

Unchanged from v1, with buildings joining walls: a sensible-route enemy rolls when the two fields' next cells differ and the direct field's parent chain crosses a pile, wall or building within 40 steps. Chance 5% for a pile, 3% for a wall or building. Once per obstacle cell; on success it takes the direct route until its direct-field value drops below the obstacle cell's value.

### Wave-tail push-through

- In the wave tail (`Waves.in_wave_tail()`: Enemies left ≤ 10 + 2 × the wave number), when the sensible field changes, each sensible-route enemy compares its sampled heading before and after the change. If the new heading turns it by more than the turn-back angle (90°), it takes the direct route instead, with the first obstacle on the direct field's chain as its obstacle, locked in as with a roll.
- Changing route while still heading forward stays allowed. The direct-route roll is unchanged. The check runs only on ticks where the sensible field changed.

## 8. Enemies

Sources: ADR 0001, [Swarm spread and speed variety](https://github.com/vandelay87/pile-up/issues/60).

- Storage, the spatial hash, separation, collision, jam detection and removal are unchanged from v1, except that leaks are gone.
- **Stats:** 10 HP (growing ×1.05 per wave), 2 cells/s, 1 gold bounty.
- **Swarm spread**, ported from `prototype/swarm-spread` (never merged), each a setting:
  - **Pace:** each enemy rolls a speed multiplier at spawn within ±3%.
  - **Wander:** each enemy weaves within ±30° of its flow heading over a 4 s period, starting at its own seeded phase. It adds to the fixed heading offset.
  - **Personal space:** a soft push between neighbours within 0.7 cells, wider than separation, capped at one step of movement per tick.
  - **Clump spawning** belongs to `Waves` (section 13).
- **Movement (step 4):** sample the route field's direction; rotate by heading offset plus wander; speed = base × pace × (1 − slow of the pile underneath); add separation and personal space; resolve collision against rock, walls, buildings and the base; route rolls, returns and wave-tail push-through; structure attacks.

## 9. Piles and walls

Sources: [Where bodies land](https://github.com/vandelay87/pile-up/issues/51), [Pile decay on a roll](https://github.com/vandelay87/pile-up/issues/61).

### Levels

| Level | Effect |
|---|---|
| 1 | 15% slow |
| 2 | 30% slow |
| 3 | 45% slow |
| 4 | 60% slow |
| 5 | Wall: impassable to walking, 15 HP |

### Landing

Bodies queued at step 7 land at step 1 of the next tick, in death-list order.

1. A body lands on the cell its enemy died on, adding a level, or starting a level-1 pile. Nothing pulls it towards a nearby pile.
2. If that cell is not a **valid landing cell** (it is a wall, rock, the base or a building's cell), the body goes to the nearest valid cell, by Euclidean distance from the enemy's exact death position to the cell's centre, ties to the lowest (y, x). The search has no distance limit, so no body is lost, and a body spilled at a structure stays on the side the enemy was on.
3. A pile reaching level 5 becomes a wall at full HP.

This replaces v1's "tallest pile within 1 cell" rule and its spill rule. A body appears on its cell at once, with no landing animation.

### Walls

`damage_wall(cell, amount)` lowers HP at once; a bucket change joins the change list. At 0 HP the wall drops to a level-3 pile at once, mid-wave.

### Decay

- At wave end, every pile rolls once with the piles' own seeded RNG, in (y, x) order: levels 1–4 lose one level 50% of the time, walls 25%. A level-1 pile that loses its roll vanishes; a wall that loses drops to level 4 and its HP is discarded.
- A pile never loses more than one level per wave end. A wall that survives keeps its damage into the next wave. A pile that climbs back to a wall comes back at full HP.
- Decay triggers the worker rebuild (section 7). Nothing warns which piles will decay.

## 10. Buildings and the power grid

Sources: [Power grid](https://github.com/vandelay87/pile-up/issues/52).

### Buildings

| Kind | Footprint | Cost | HP | Power area |
|---|---|---|---|---|
| Tower | 2×2 | 80 | 60 | 4 |
| Pylon | 1×1 | 20 | 20 | 10 |
| Repair yard | 2×2 | 80 | 60 | 4 |
| Base (not a building) | 4×4 | – | 200 | 10 |

### Power

- A **power area** is the square reaching its size in cells from the footprint's edge (Chebyshev distance), ignoring piles, walls and rock. The base's area is 24×24 cells.
- **Powered:** the base is always powered. A building is powered when any of its cells lies in the power area of the base or of another powered building. `PowerGrid.recompute` walks outwards from the base through these overlaps; an unpowered building powers nothing.
- **The power grid** is every cell in the power area of the base or of a powered building.
- **Recompute** runs whenever the set of buildings changes: a build at step 0 or a destruction at step 4. `power_changed` is emitted when any building's powered flag or the grid changes.
- **Unpowered buildings** stop working (a tower stops firing; a repair yard's drone flies home and stops) but stay structures: they keep their HP, block routes, can be attacked and hold their cells. Power returns at once when a new building links them back up.

### Placement (step 0)

`Buildings.can_place(kind, origin)`: every footprint cell is in bounds, on the power grid, and clear (no rock, base, building or pile) → `RunState.can_afford(cost)`. On success, gold is charged, the cells are written to `Occupancy`, a field update is queued, power is recomputed and `building_placed(id)` is emitted. On failure, `command_rejected(reason)` with "off the power grid", "occupied" or "not enough gold". Building is allowed during waves and in the build phase. No selling or demolishing.

## 11. Towers

Sources: [Tower attacks: projectiles or instant hits](https://github.com/vandelay87/pile-up/issues/13).

Unchanged from v1 except for the numbers and power: 5 damage, 3.5 shots/s, range 8 cells from the footprint's centre, aimed at the enemy closest to the base (lowest sensible-field value, ties to the lowest id), instant hits, firing in build order, cooldown in ticks, ready on the tick it is built. Only powered towers fire; an unpowered tower keeps its cooldown and is ready when power returns. Each tower counts its kills this run for the stats panel.

## 12. Repair yards

Sources: [A building that heals](https://github.com/vandelay87/pile-up/issues/67).

### The drone

Each repair yard has one drone, created with it and destroyed with it. It is never attacked and ignores terrain. A drone's state is one of:

```
HOME ──pick──▶ OUTBOUND(target) ──arrive──▶ REPAIRING(target) ──full──▶ RETURNING ──arrive──▶ HOME
                    │  target destroyed: pick again from where it is  │
                    └──────── yard unpowered, or wave end ──▶ RETURNING ◀──┘
```

- It flies in a straight line at 8 cells/s between the yard's centre and the target's centre, and repairs at 5 HP/s until the target is at full HP. Drones on the same building add their rates.
- It picks a job only when HOME, or when its target is destroyed mid-trip, and only during a wave while its yard is powered. At wave end, or when the yard loses power, it returns home and stops.
- Drones step in their yards' build order, so ties are deterministic.

### Picking

- **Candidates:** damaged buildings other than the yard itself with any cell inside the yard's **repair area** (8 cells from the yard's edge, Chebyshev). Walls and the base are never repaired.
- **Assignment first:** if the yard has an assignment and it is damaged, the drone picks it.
- **Auto otherwise:** the candidate nearest the yard (distance between footprint centres), then lowest HP, then lowest id. A candidate no other drone is targeting is preferred; when every candidate is taken, the drone doubles up.
- An assignment is a building inside the yard's repair area, not the yard itself; `Assign` is rejected otherwise. It lasts until `ClearAssignment` or until the building is destroyed. A new assignment takes effect once the drone is home from its current trip.

### Stats

Each yard counts the HP it has repaired this run, for the stats panel.

## 13. Waves, run state and the combo

Sources: [Kill counter and combo](https://github.com/vandelay87/pile-up/issues/53), [Swarm spread](https://github.com/vandelay87/pile-up/issues/60), [Re-routing over long distances](https://github.com/vandelay87/pile-up/issues/59).

### Waves

- Phases, "next wave", wave size `round(20 × 1.3^(n−1))`, enemy HP growth and spawn edges (1 or 2 of the map's edges) are as in v1, with the new growth.
- **Clump spawning:** enemies spawn in bursts of 16, each on a seeded random spawn cell along the wave's edges, keeping an average of 10 per second.
- **Enemies left** = wave size − kills this wave, with unspawned enemies included. It reaches 0 exactly as the wave ends; in the build phase it reports the next wave's size.
- **Wave tail:** `in_wave_tail()` is true during a wave once Enemies left ≤ 10 + 2 × the wave number.
- **Wave end:** every enemy has spawned and none remain alive.

### Run state

- Base HP 200 and gold 200 at the start of a run. `damage_base` lowers base HP; at 0 the run ends and `game_over` is emitted. After it, the simulation accepts only a restart.
- **Kills** counts the run's kills.

### Combo

- The **tier** is set by the number of kills in the last 2 s (a sliding window counted in ticks): ×1 below 10, ×2 from 10, ×3 from 20, capped at ×3.
- Each kill pays bounty × the current tier at once, the tier updated kill by kill within a tick's death list, so gold earned mid-burst can be spent during the wave.
- Only a falling kill rate lowers the tier. Damage to the base or buildings does not.
- `combo_changed(tier)` is emitted when the tier changes, and `payout(amount, tier)` once per tick with the tick's total when any kill was multiplied.

## 14. View

The v1 view stands: plain coloured shapes from one committed atlas, one y-sorted world, pooled enemy canvas items, pile lift, hit flash, tracers, pan and zoom. v2 adds:

- **Atlas:** pylon, repair yard, drone, an unpowered icon and a repair effect, drawn by `tools/make_atlas.gd`.
- **Buildings:** towers, pylons and repair yards drawn from `building_placed` and removed on `building_destroyed`. An unpowered building is drawn greyed out with the unpowered icon.
- **Drones** are drawn each frame from `RepairYards`' positions, above the y-sorted world. A building being repaired shows a small steady repair effect.
- **Placement:** buttons or keys for each kind (**T** tower, **P** pylon, **R** repair yard). While placing, the power grid's cells are tinted and the ghost is green only when `can_place` and `can_afford` pass. A repair yard's ghost also tints its repair area. Left-click places and stays in placement mode; right-click or **Esc** leaves it.
- **Selection:** clicking a building or the base selects it; clicking empty ground or pressing **Esc** clears it (Esc leaves placement mode first). The selection shows its range (a tower's fire range, a repair yard's repair area, a pylon's or the base's power area) and a stats panel: HP and max HP and whether it is powered; a tower adds damage, shots/s, range and its kills; a repair yard adds its repair rate, auto or its assignment, an assign control (the next click on a building in its area becomes the assignment) and a clear control, and its HP repaired; a pylon adds its power area. A destroyed selection clears itself.
- **HUD:** gold (flashing on a multiplied payout), base HP, wave number, **Enemies left**, **Kills**, the combo tier (hidden at ×1, pulsing and growing on each tier-up, fading as it falls), and the "next wave" button. The game-over panel shows the wave reached and Kills. Lives are gone.
- **UI scaling:** the HUD, panels and toasts scale with the window, so they read at a comfortable size at full screen on the baseline MacBook.

## 15. Debug panel and overlays

The v1 panel, stats readout and overlays stand, and the panel grows with the new settings. v2 adds two overlays, off at launch:

## 16. Testing, CI and performance

Sources: [Testing, CI and performance checks](https://github.com/vandelay87/pile-up/issues/10).

### The test seam

- **The Simulation is the seam.** v2 rules are tested by building a `Simulation` on a tiny inline map (`TestMaps.from_rows`) with fixed settings and seed, queueing commands, running ticks, and asserting on its public state (building HP and powered flags, drone state and position, gold, base HP, Kills, Enemies left, the combo tier, pile levels) and the end-of-tick signals. Tests set up a situation, as a player or the debug panel could, and check what comes out; they do not reach into a system's private arrays.
- **Kept seams:** the routing exactness test (an incremental update equals a full rebuild) stays at `Routing`, since the Simulation cannot see it; `bench_sim` and the local frame benchmark stay the performance seam.
- Existing v1 tests at system level that v2 rules change (landing, decay, leaks, lives, `would_block`) are rewritten or removed by the ticket that changes the rule.
- Each build ticket's acceptance criteria name the tests it adds, written test-first. Prior art: `test/sim/simulation_test.gd`, `test/sim/waves/next_wave_test.gd`, `test/sim/run_state_test.gd`, `test/sim/enemies/walls_test.gd`.
- Rendering, input and UI (placement tints, selection, stats panel, HUD, scaling) have no automated tests; the human checks them in playtests.

### CI and performance

- CI is unchanged: `lint`, `test`, `sim-budget` and `export`, all required on every PR.
- `bench_sim.gd` grows to include buildings under attack, a destroyed pylon cutting off a branch, and drones repairing, alongside the dense crowd, changing piles and a decay rebuild. Its limit changes only in a PR that explains why.
- PRs that touch the enemy module, flow fields, the tick driver, power, drones or drawing paste the local M5 table in the PR's Performance section.

## 17. Rechecks after the build

Not build tickets; checked in the playtest that closes v2 (the last ticket):

- Tightly bunched enemies jittering beside towers: recheck once towers are attackable, and diagnose it if it remains.
