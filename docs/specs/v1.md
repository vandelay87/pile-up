## 1. Platform and engine

- Godot 4.7.2, standard build, typed GDScript. The version is pinned in one CI workflow variable; an upgrade is a deliberate PR made together with the local editor.
- Platforms: macOS and Windows. Baseline machine: Apple M5 MacBook, 16 GB RAM.
- Performance target: about 1,000 enemies at 60 fps on the baseline machine. Measured headroom: the spike held 60 fps to about 6,000 enemies ([Spike: 1,000 enemies on a flow field](https://github.com/vandelay87/pile-up/issues/7)).
- No C# in v1. If a hot loop ever has to leave GDScript, it moves to a C++ GDExtension behind the same module interface ([Can GDScript move 1,000 enemies within budget?](https://github.com/vandelay87/pile-up/issues/6)).

## 2. Architecture

Source: [Code organisation and system boundaries](https://github.com/vandelay87/pile-up/issues/11), ADR 0001, ADR 0002.

- **Simulation and view.** All game rules live in one node-free `Simulation` (`RefCounted`) that owns every system, their seeded RNGs and the tick driver. A view layer of nodes draws it and turns input into commands. One `Main` scene builds the `Simulation` and calls `tick()` from `_physics_process` at a fixed 60 Hz. There is no render interpolation in v1.
- **Boundary rule.** Nothing under `src/sim/` extends `Node`, `Node2D` or `Resource`, or references `src/view/`. The `lint` CI job enforces this.
- **Commands.** Tower builds, "next wave", restart and every debug-panel action are queued as commands and drained at tick step 0. A seed plus a list of (tick, command) pairs replays a run exactly. A failed command returns through the `command_rejected(reason)` signal.
- **Inside the simulation.** Systems never connect to each other by signal. The tick driver calls them in a fixed order and passes data explicitly; for example, the enemy removal step returns death and leak lists, which the driver hands to `Piles` and `RunState`.
- **Out to the view.** Sparse changes leave the simulation as signals emitted at the end of a tick: `pile_changed`, `tower_placed`, `gold_changed`, `lives_changed`, `phase_changed`, `wave_started(edges)`, `fields_changed`, `shots_fired(shots)`, `command_rejected(reason)`, `game_over`. The enemy renderer and the overlays read packed arrays read-only each frame instead.
- **Determinism.** Each system receives its own seeded RNG; nothing calls the global `randf()`.
- **Restart.** A new run builds a fresh `Simulation` with the same `MapData` and a new seed. No system supports resetting itself. After `game_over`, the simulation accepts only a restart.

### Systems

| System | Owns | Interface (main parts) |
|---|---|---|
| `MapData` | Immutable loaded map: size, rock, base footprint, spawn edges and their spawn cells | `is_rock(cell)`, `is_base(cell)`, `spawn_cells(edge)` |
| `Occupancy` | Mutable tower cells | written by tower placement |
| `Piles` | Level and wall HP per cell; landing rules | `queue_bodies(positions)`, `damage_wall(cell, amount)`, `decay()`; produces a change list for `Routing` |
| `Routing` | Both flow fields | incremental update from a change list, `start_rebuild()`, `would_block(cells)`, `sample_direction(route, pos)`, `sample_value(route, pos)` |
| `Enemies` | Packed enemy arrays and the spatial hash | `spawn(cell_pos)`, `damage(id, amount)`, `nearest_to_base_in_range(pos, range) -> id`; removal step returns death and leak lists |
| `Towers` | Typed array of `Tower` objects (cell, cooldown, target id) in build order | `can_place(cell)`; builds the per-tick shot list |
| `Waves` | Spawn schedule, the wave's spawn edges, wave-end detection, phase | |
| `RunState` | Gold, lives, wave number, game over | `can_afford(cost)` |

## 3. Tick order

Source: [Code organisation and system boundaries](https://github.com/vandelay87/pile-up/issues/11). This order supersedes the five-step order in ADR 0001.

0. Drain commands (tower placement, next wave, restart, settings changes, debug actions).
1. `Piles` lands bodies queued last tick. On the tick after a wave end, `Piles.decay()` and `Routing.start_rebuild()` run next, so the last kills' bodies decay with their wave. `Routing` applies the change list (pile level changes, towers built, wall HP bucket changes, walls broken) as an incremental field update, and swaps in the decay rebuild once it is due.
2. `Waves` spawns.
3. Rebuild the spatial hash.
4. Move enemies: flow field, pile slow, separation, collision, route rolls, wall attacks. Wall damage changes wall HP at once; any rerouting follows at step 1 of the next tick.
5. Towers target and damage.
6. Remove dead and leaked enemies. Deaths go to `Piles.queue_bodies`; kill and leak counts go to `RunState`.
7. `Waves` checks for wave end; on wave end, decay becomes due at step 1 of the next tick, and the phase becomes build phase.

Then the end-of-tick signals are emitted. Removal waits until step 6, so enemy ids and indices are stable for the whole tick.

## 4. Settings

Source: [Settings file and debug panel](https://github.com/vandelay87/pile-up/issues/15).

- **Tunable:** every gameplay number in `docs/design.md`, plus the knobs listed in later sections (marked *setting*). Structural values stay constants in code: tick rate, tower footprint (2×2), the five pile levels, and the "within 1 cell" landing radius.
- **File:** `data/settings/defaults.json` holds values only, grouped by system (`enemies`, `piles`, `routing`, `towers`, `waves`, `run`, `view`), in the units of `docs/design.md` (seconds, per second, percent, cells).
- **Schema:** one table in `src/sim/settings.gd` gives each setting its type, min, max, step, unit, and whether it is `live` or `restart`. The typed `Settings` object beside it converts to tick units on read (for example `cooldown_ticks`), so conversions live in one place.
- **Validation:** loading fails with a clear error, and nothing loaded, on an unknown key, a missing key, a wrong type, an out-of-range value or a value off its step. A unit test checks that the committed defaults file passes.
- **Use:** each system receives the shared `Settings` object at construction and reads values when it uses them.
- **Live and restart:** a change is a step-0 command. A `live` setting applies on that tick; a route-weight change triggers a full field rebuild there. A `restart` setting (starting lives and gold, map path, wave 1 size) is stored and applies when the next `Simulation` is built.
- **Growth:** the settings file and schema grow with the build tickets. Each ticket adds the settings its system reads.

## 5. Map and grid

Sources: [Map data format](https://github.com/vandelay87/pile-up/issues/12), [Isometric grid in Godot 4.7](https://github.com/vandelay87/pile-up/issues/4), [Flow field design](https://github.com/vandelay87/pile-up/issues/9).

### File format

`data/maps/v1.json`: a JSON header followed by the terrain as ASCII rows, one string per row.

- `version` (starts at 1)
- `width`, `height`
- `rows`: `.` is a clear cell, `#` is rock. Rows run along grid y and characters along grid x, with (0,0) top-left, matching TileMapLayer map coordinates.
- `base`: origin cell plus size
- `spawn_edges`: a subset of `N`/`E`/`S`/`W`

Gameplay numbers (lives, gold, waves) are not in the file; they stay in settings. **Derived at load:** the base cell set, and each spawn edge's spawn cells (its passable cells that reach the base, so a rock pocket on an edge never spawns).

### Validation

`MapData` loading rejects, with a clear error and no partial map:

- an unknown version;
- a size over 150 cells per side, or rows whose lengths don't match;
- an unknown character;
- a base out of bounds or on rock;
- a listed spawn edge with no passable cell that reaches the base.

Each rule is unit-tested with tiny inline maps. Hand-made and generated maps pass the same check. Rock pockets cut off from the base are allowed.

### The v1 map

120×120 cells; a 4×4 base at the centre; all four spawn edges. Three or four rock formations create natural chokepoints (a ridge or two plus a few scattered boulders), and every edge stays well connected to the base. Claude writes the map from this brief; the human reviews it in the game and in the diff.

`Main` loads `MapData` from the `map_path` setting (default `res://data/maps/v1.json`) and passes it to the `Simulation`.

### Rock

No enemy can enter rock, and nothing can be built or land on it. It costs infinity in both flow fields. For bodies it behaves like a tower cell (see [Landing](#landing)).

### Grid maths

- Simulation positions are float cell coordinates (grid space). Speed, separation radius, tower range and reach are all in cells.
- The terrain is a `TileMapLayer` with an isometric `TileSet` in `TILE_LAYOUT_DIAMOND_DOWN`. The TileSet default is `STACKED`, which must be changed.
- All cell/world maths goes through one `Transform2D` in `grid_transform.gd`: `Transform2D(Vector2(W/2, H/2), Vector2(-W/2, H/2), Vector2(W/2, 0))` for tile width W and height H. `xf * (cell + 0.5)` equals `map_to_local`; `floor(xf.affine_inverse() * p)` equals `local_to_map`; the unfloored inverse gives the float grid position.
- Mouse picking: `layer.local_to_map(layer.get_local_mouse_position())`.
- Edges: code and file use grid N/E/S/W. On screen, a wave announcement highlights that side of the diamond rather than naming it, since grid north appears as the top-right side.

### Camera

One `Camera2D`. Drag to pan (`position -= relative / zoom`); zoom towards the cursor by correcting the position by the change in mouse world position; limits keep the view on the map. Camera input is handled in `_unhandled_input`, so the UI gets events first. At default zoom the map is about 1.5–2 screens wide.

## 6. Routing

Sources: [Flow field design](https://github.com/vandelay87/pile-up/issues/9) as amended by [Crowd behaviour at walls](https://github.com/vandelay87/pile-up/issues/14); [Flow field cost in GDScript on a large grid](https://github.com/vandelay87/pile-up/issues/3).

### Fields

- Two fields over the whole grid: **sensible** and **direct**. Each is an integration field (cost to the base) plus each cell's true shortest-path parent.
- **Goal:** the base cells are the zero-cost seeds of both fields. An enemy that enters a base cell leaks.
- **Steps:** octile (1 straight, √2 diagonal). No corner cutting: a diagonal step needs both orthogonal neighbours walkable.
- **Parents:** each cell stores its true shortest-path parent (the neighbour minimising neighbour value plus step cost), not merely its lowest neighbour. The incremental update depends on this.

### Costs

One formula for both fields: cost to enter a cell = `step × terrain factor`.

| Cell | Terrain factor |
|---|---|
| Clear | 1 |
| Pile at level L (1–4) | `1 + pile_weight × (1/(1 − slow(L)) − 1)` |
| Wall | `1 + wall_weight × break_time_in_cells` |
| Tower, rock | infinite |

- `break_time_in_cells` = remaining HP ÷ wall damage per second × enemy speed. A fresh 30 HP wall at 1 dps and 1.5 cells/s is 45 cells.
- Wall HP enters the cost in buckets (*setting* `wall_hp_bucket`, default 10 HP). Each bucket change queues one field update.
- Weights (*settings*): sensible `pile_weight = 1`, `wall_weight = 1`; direct `pile_weight = 0`, `wall_weight = 0.1`.

### When the fields change

| Event | Update |
|---|---|
| Map load | Synchronous full rebuild of both fields |
| Pile level change, tower built, wall bucket change, wall broken | Queued; applied at tick step 1 as an incremental update (Ramalingam–Reps style) on the main thread, batched per tick |
| End-of-wave decay | Full rebuild of both fields as two `WorkerThreadPool` tasks, swapped in at step 1 a fixed `DECAY_REBUILD_TICKS` (12) ticks after it starts. The main thread waits if the worker has not finished by then, so the swap tick never depends on wall-clock time and replays stay exact. A change during the rebuild restarts it when it is due, with a new delay. "Next wave" stays disabled from wave end until the swap |
| Route-weight setting change | Synchronous full rebuild at step 0 |

**Incremental update:** when a cell's cost rises, the subtree of the shortest-path tree through it is invalidated and re-seeded from its border; when a cost falls, values propagate only while they improve. The result must equal a full rebuild exactly. Measured: median 0.03 ms per change, worst case about 19 ms for a cell beside the base. Full rebuild at 120×120 is about 30 ms per field.

`Routing` emits `fields_changed` (for overlays) after any update.

### Blocking

A tower placement is rejected if any open spawn-edge cell, or any live enemy's cell, would lose its route to the base (`would_block(cells)`). Walls never block, since their cost is finite.

### Sampling

- **Direction:** an enemy steers by bilinearly blending the direction vectors of the 4 cells around its float position, skipping impassable cells, so headings are continuous rather than 8-way.
- **Value:** the same 4-cell bilinear blend over the integration field. Towers use it to rank enemies; enemies use it for route returns and jam detection.

### Route rolls

- Every enemy starts on the sensible route.
- A sensible-route enemy **rolls** when the two fields' next cells from its position differ, and the direct field's parent chain from there crosses a pile or wall within 40 steps. That first pile or wall cell is the **obstacle**. Chance: 5% for a pile, 3% for a wall (*settings*).
- It rolls once per obstacle cell, remembering the last cell it rolled on.
- On a success it switches to the direct route. It returns to the sensible route once its own direct-field value drops below the obstacle cell's value. This still holds if the wall breaks or the pile decays meanwhile.
- A wide field of scattered piles offers several rolls; this is accepted.

## 7. Enemies

Sources: [Enemy simulation and rendering architecture](https://github.com/vandelay87/pile-up/issues/8) (ADR 0001), [Crowd behaviour at walls](https://github.com/vandelay87/pile-up/issues/14), [Drawing 1,000+ enemies in Godot 4.7 2D](https://github.com/vandelay87/pile-up/issues/2).

### Storage

- Parallel typed packed arrays in one module (position, HP, route, heading offset, last rolled cell, obstacle value, jam timer, wall target, hit flash, and so on), dense, with swap-remove on death.
- Each enemy has a stable id with an id→index lookup, so a tower can hold a reference across removals.
- Arrays grow by doubling. Other systems reach enemies only through the module interface (section 2).

### Stats

10 HP (growing per wave, section 10), 1.5 cells/s, 1 gold bounty (*settings*). HP is a float.

### Movement (step 4)

1. Sample the direction from the enemy's current route field and rotate it by the enemy's heading offset. The offset is a seeded random angle fixed at spawn, within ±`heading_offset` (*setting*, default 10°, 0 disables it).
2. Speed is base speed × (1 − slow of the pile under the enemy).
3. Add separation (below).
4. Resolve collision: an enemy inside a rock, wall or tower cell is pushed out through the cell's nearest open side. The same rule handles a wall forming under enemies.
5. Route rolls and returns (section 6).
6. Wall attacks (below).
7. An enemy whose cell is a base cell is marked leaked.

### Separation

- Spatial hash with one-cell buckets, rebuilt every tick at step 3 by counting sort into packed arrays. Each enemy checks the 3×3 neighbouring buckets.
- *Settings:* `separation_radius`, `separation_push`, `neighbour_cap` (default off).
- Wall attackers hold their ground: the crowd behind cannot push them. Attackers still push each other.

### Attacking walls

- **Which wall:** if an enemy's route crosses a wall within 2 steps, it attacks the nearest wall cell it is pressed against: within `separation_radius + wall_reach` of the cell's square (*setting* `wall_reach`, default 0.1 cells). It does not have to be the exact cell its route steps into.
- **Damage:** each attacker deals 1 HP per second (*setting*) to its wall via `Piles.damage_wall`. There is no limit on attackers beyond space; separation fits about 2 per wall-cell face.
- **Finish:** an attacker keeps hitting its wall until the wall falls or the attacker is pushed out of reach, even if its route changes.
- **Jam:** an enemy that makes no progress along its route field (its sampled value does not drop) for `jam_seconds` (*setting*, default 0.5 s) and is pressed against any wall attacks it, then finishes it. Breaches widen under crowd pressure; this is accepted.
- **No giving up:** a direct-route enemy stuck behind attackers stays on the direct route until it is past the obstacle.
- **Wall falls:** attackers on it go back to walking.

### Removal (step 6)

Enemies with HP ≤ 0 and leaked enemies are swap-removed. The step returns a death list (positions) and a leak count. Their canvas items are hidden and returned to the pool.

## 8. Piles and walls

Sources: `docs/design.md`, [Map data format](https://github.com/vandelay87/pile-up/issues/12), [Code organisation and system boundaries](https://github.com/vandelay87/pile-up/issues/11).

### Levels

| Level | Effect |
|---|---|
| 1 | [15% slow](https://github.com/vandelay87/pile-up/issues/19) |
| 2 | [30% slow](https://github.com/vandelay87/pile-up/issues/20) |
| 3 | [45% slow](https://github.com/vandelay87/pile-up/issues/21) |
| 4 | [60% slow](https://github.com/vandelay87/pile-up/issues/22) |
| 5 | [Wall: impassable to walking, 30 HP](https://github.com/vandelay87/pile-up/issues/23) |

The slow percentages and wall HP are settings; the number of levels is a constant.

### Landing

Bodies queued at step 6 land at step 1 of the next tick, in death-list order:

1. A body joins the tallest pile within 1 cell of its death cell (the 3×3 block), skipping walls. Ties go to the death cell, then the lowest (y, x).
2. If no pile is within 1 cell, it starts a new level-1 pile on its death cell.
3. If the chosen cell is not a valid landing cell, the body moves to the nearest valid cell (breadth-first from the death cell, octile order, ties to the lowest (y, x)).

A **valid landing cell** is clear or a pile below level 5, and not a tower, rock or base cell. Excluding walls is what makes bodies of enemies killed at a wall spill into the nearest non-wall cell, so defending a wall thickens it. A pile reaching level 5 becomes a wall with full HP.

### Walls

- `damage_wall(cell, amount)` lowers HP at once. A bucket change adds the cell to the change list.
- At 0 HP the wall falls back to a level-3 pile and the cell is added to the change list.

### Decay

At wave end, every pile loses one level; level-1 piles vanish. A wall decays to level 4, and its HP is discarded. Decay triggers the full field rebuild on the worker (section 6).

### Output

`Piles` produces the per-tick change list for `Routing` and emits `pile_changed(cells)` at tick end.

## 9. Towers

Sources: [Tower attacks: projectiles or instant hits](https://github.com/vandelay87/pile-up/issues/13), [Code organisation and system boundaries](https://github.com/vandelay87/pile-up/issues/11).

### Stats

3 damage, 2 shots/s, range 8 cells, 50 gold, 2×2 footprint (*settings*, except the footprint).

### Placement (step 0)

`Towers.can_place(cell)` (all four cells are clear: no rock, base, tower or pile) → `RunState.can_afford(cost)` → `Routing.would_block(cells)`. On success, gold is charged, the cells are written to `Occupancy`, a field update is queued and `tower_placed` is emitted. On failure, `command_rejected(reason)` is emitted ("blocked", "occupied", "not enough gold"). Building is allowed during waves and in the build phase.

### Firing (step 5)

- Towers fire in build order, keeping the tick deterministic.
- **Cooldown** is counted in ticks (30 at 60 Hz for 2 shots/s), read from settings when the tower fires. An idle tower stays ready: it fires on the first tick an enemy is in range, and a new tower is ready on the tick it is built.
- **Range** is the Euclidean distance in cells from the centre of the 2×2 footprint to the enemy's float position.
- **Targeting:** every shot re-queries `nearest_to_base_in_range`. Enemies are ranked by sensible-field value (bilinear sample), lowest first; ties go to the lowest id. One field for all enemies keeps direct-route enemies comparable. Enemies with HP ≤ 0 are skipped.
- **Hit:** damage applies at once; there is no projectile state. An enemy dies where the shot hit it, so its body lands from there. `Tower.target_id` holds the last-shot target.
- **Shot list:** each shot adds (tower id, target id, hit position) to a per-tick list, emitted once at tick end as `shots_fired(shots)` when not empty.

A later slow-shot tower can add a simulated `Projectiles` system at step 5 without changing these targeting rules.

## 10. Waves and run state

Sources: `docs/design.md`, [Code organisation and system boundaries](https://github.com/vandelay87/pile-up/issues/11).

### Run state

- Starting lives 20, starting gold 150 (*restart settings*).
- A kill adds the bounty; a leak removes 1 life. At 0 lives `RunState` emits `game_over`.

### Waves

- **Phases:** build phase and wave. A run starts in the build phase at wave 0.
- **Next wave:** a step-0 command, accepted only in the build phase with no decay rebuild in flight.
- **Size:** wave n has `round(wave_1_size × growth^(n−1))` enemies (wave 1 size 20, growth 1.2; *settings*). Enemy HP is `base_hp × hp_growth^(n−1)` (growth 1.05).
- **Spawn edges:** each wave picks 1 or 2 edges at random from the map's `spawn_edges` (*setting* `second_edge_chance`, default 50%), emitted as `wave_started(edges)` so the view can announce them.
- **Spawning:** enemies spawn at `spawn_rate` per second (*setting*, default 10/s), spread evenly over the chosen edges, each at a seeded random spawn cell of its edge (cell centre plus a small seeded jitter).
- **Wave end:** when every enemy of the wave has spawned and none remain alive. The phase returns to build phase at step 7, and decay and the rebuild start at step 1 of the next tick.
- Waves are endless.

## 11. View

Sources: [Enemy simulation and rendering architecture](https://github.com/vandelay87/pile-up/issues/8), [Isometric grid in Godot 4.7](https://github.com/vandelay87/pile-up/issues/4), [Tower attacks: projectiles or instant hits](https://github.com/vandelay87/pile-up/issues/13), and this ticket.

### Art

- Plain coloured shapes, as white textured rects tinted with modulate. Polygons are not used, because they never batch.
- One committed atlas, `assets/atlas.png`, produced by `tools/make_atlas.gd` and checked in: iso tiles (clear, rock), base, tower, enemy, tracer streak, and pile blocks that read as stacked blocks darkening per level. Final art later replaces the file without code changes.

### World layers

- Terrain: `TileMapLayer` (section 5).
- One y-sorted parent shared by piles, towers, the base and enemies, so they interleave correctly.
- Piles: a second y-sorted `TileMapLayer` with one atlas tile per level; each level change is one `set_cell` or `erase_cell`, driven by `pile_changed`.
- Enemies: one pooled `RenderingServer` canvas item per enemy under the y-sorted parent, origin at the foot. Canvas items are hidden and reused, never freed. Each frame the renderer reads positions from the enemy arrays and writes transforms through the grid transform.
- An enemy standing on a pile is drawn lifted by the pile's height, eased between levels, while its y-sort position stays at the ground foot point.
- A hit gives the enemy a ~0.1 s white flash via modulate, starting when the tracer arrives.
- Tracers: each shot in `shots_fired` is a pooled `RenderingServer` streak that reads as a tracer shell, flying from the tower to the hit position at `tracer_speed` (*setting*, default 60 cells/s) on a layer above the y-sorted world. A killing round may finish its flight just after the enemy disappears; this is accepted.

### HUD

- Gold, lives and wave number, plus a "next wave" button that is disabled during a wave and while a decay rebuild is in flight.
- At wave start, the spawn edges are highlighted on the matching sides of the diamond.
- **Tower placement:** a tower button or the **T** key enters placement mode. A 2×2 ghost follows the cursor, green when valid and red when not. Left-click places and stays in placement mode; right-click or **Esc** leaves it. The ghost checks only `can_place` and `can_afford`; a placement that would block the route turns red only once its command is rejected.
- A rejected command shows its reason as a short toast.
- No selling or upgrading.
- **Game over:** a panel with the wave reached and a restart button.

## 12. Debug panel and overlays

Source: [Settings file and debug panel](https://github.com/vandelay87/pile-up/issues/15).

- **Panel (F1):** generated from the settings schema. One collapsible section per system; each row has a slider (range and step from the schema), a number field and a reset-to-default button. Rows that differ from the file are highlighted, and restart-only rows are marked "applies on restart". It ships in every v1 build, hidden by default.
- **Save:** writes the current values, including pending restart values, back to `data/settings/defaults.json`. It is available only when running from the project folder and is disabled in exports.
- **Time controls and cheats** (step-0 commands, so replays still match): pause, step one tick, speed ×1/×2/×4 (the sim runs N ticks per physics frame), add gold, jump to wave N.
- **Stats readout (F2):** fps, enemy count, tick cost (mean and max over the last second, measured by the tick driver), and whether a decay rebuild is in flight.
- **Overlays** (checkboxes on the panel, no hotkeys, all off at launch, not saved): flow arrows per route; field-value heatmap per route; pile labels (level, plus remaining HP on walls); enemy route tint; tower range circles.
- **Overlay data:** overlays read `Routing` and `Piles` arrays read-only and redraw only on `fields_changed` or `pile_changed`. Route tint reads the enemy route array each frame.
- Each overlay ships with the ticket that creates its data (section 14).

## 13. Testing, CI and performance

Sources: [Testing, CI and performance checks](https://github.com/vandelay87/pile-up/issues/10), [Testing and CI for Godot 4.7](https://github.com/vandelay87/pile-up/issues/5).

### Tests

- gdUnit4 v6.2.1 committed to `addons/gdUnit4`. Tests live in `test/`, mirroring source paths, as `*_test.gd`.
- Simulation rules are tested in plain `RefCounted` classes with no scene tree, test-first. Each build ticket's acceptance criteria name the tests it adds.
- Rendering, input and UI have no automated tests in v1; they are checked by the human in playtests.

### Static checks

`gdlint` and `gdformat --check`; untyped declarations and unsafe calls set as errors in `project.godot`; the sim/view boundary rule (section 2).

### CI

- Four parallel jobs on every PR, all required: `lint`, `test` (gdUnit4's official GitHub Action under xvfb, `version: installed`), `sim-budget`, `export`.
- `export` builds Windows and an ad-hoc-signed macOS `.zip` in one Ubuntu job with cached export templates, uploaded as artifacts kept for 7 days.
- `main` is branch-protected: CI must pass and direct pushes are blocked.

### Performance

- **Simulation budget (CI):** `tools/bench_sim.gd` runs the whole tick driver headless with a fixed seed: 1,000 enemies in a dense crowd near the base, piles changing during the run, and a decay rebuild, for ~600 ticks after a warm-up. It fails when the mean tick cost exceeds 3× the CI mean measured when the check lands. The limit is a constant that changes only in a PR that explains why.
- **Frame time (local):** a benchmark scene grown from the spike's `--bench` mode (branch `prototype/enemy-spike`, `prototypes/enemy_spike/`) runs the real systems with vsync off. It passes when 1,000 dense enemies hold a p99 frame time under 16.6 ms, and it reports the largest enemy count that holds 60 fps.
- The PR template has a "Performance" section. PRs that touch the enemy module, flow fields, the tick driver or drawing paste the local M5 table there; other PRs state "n/a".
- Profiling is done with vsync off: with vsync on the M5 clocks down and the same work measures about 4× slower. GPU time cannot be read on Metal.
