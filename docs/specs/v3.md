# Prototype v3 spec: pressure

This spec gathers every technical decision for prototype v3 in one place and ends in the ordered list of build tickets. v3 is about **pressure**: the v2 playtest showed a late game that no wave could break, so a crowd that stalls against a defence now builds up until it tumbles over it, and the player gets new tools to answer that. v3 adds overflow, the grinder, the bloater, per-building combos, repair as a trade-off, a flared and bigger map, and a bottom HUD.

It is self-contained: where v3 keeps a v2 rule, the rule is restated here, and `docs/specs/v2.md` stays frozen as history. Game rules and their starting numbers come from `docs/design.md`; vocabulary from `GLOSSARY.md`. If this spec and a closed ticket disagree, this spec is current. Planned in [Map: prototype v3 spec](https://github.com/vandelay87/pile-up/issues/92).

## 1. Platform and engine

Unchanged from v2.

- Godot 4.7.2, standard build, typed GDScript, pinned in one CI workflow variable.
- Platforms: macOS and Windows. Baseline machine: Apple M5 MacBook, 16 GB RAM.
- Performance target: about 1,000 enemies on screen at 60 fps on the baseline machine.
- No C#. A hot loop that has to leave GDScript moves to a C++ GDExtension behind the same module interface (ADR 0001).

## 2. Architecture

Sources: ADR 0001, ADR 0002, [Code organisation and system boundaries](https://github.com/vandelay87/pile-up/issues/11).

The v2 architecture stands: a node-free `Simulation` owns every system, their seeded RNGs and the tick driver; the view draws it and turns input into commands; nothing under `src/sim/` extends `Node` or `Resource` or references `src/view/`, and the `lint` job enforces it. Commands drain at step 0, so a seed plus a list of (tick, command) pairs replays a run exactly. Systems never signal each other; the tick driver passes data between them. A restart builds a fresh `Simulation`. Every building is in one `Buildings` registry, and enemies attack walls, buildings and the base through the `Structures` facade.

### What changes in v3

- **Kill credit.** Each enemy remembers the last building that damaged it (`Enemies.last_hitters`, a building id or `NONE`). The removal step returns a list of **deaths**, each with its position, kind, killer and whether a blast killed it, instead of bare positions. `RunState` pays each death by its killer's combo.
- **Two enemy kinds.** `Enemies` gains a kind slot (`NORMAL` or `BLOATER`) and a fuse slot. Kind-specific numbers (HP, speed, bounty) are read per kind.
- **New systems:** `Overflow` (crushes, their gauges, and every tumble in flight), `Combos` (each building's combo) and `Blasts` (resolving bloater blasts at the removal step). The global combo leaves `RunState`.
- **Working.** A building works when it is powered and not under repair (a pylon ignores repair). `Buildings.is_working(id)` is the one check towers, grinders and drones read.
- **Grinders** are a fourth building kind. They damage enemies at the same step as towers fire.
- **The map** gains no-build cells.

### Systems

| System | Owns | Interface (main parts) |
|---|---|---|
| `MapData` | Immutable loaded map | `is_rock(cell)`, `is_base(cell)`, `is_no_build(cell)`, `spawn_cells(edge)` |
| `Occupancy` | Building id per cell | written by `Buildings` on build and destruction |
| `Piles` | Level and wall HP per cell; landing and decay | `queue_bodies(deaths)`, `damage_wall(cell, amount)`, `erase(cell)`, `decay(rng)`; change list for `Routing` and `Overflow` |
| `Routing` | Both flow fields | as in v2 |
| `Enemies` | Packed enemy arrays (kind, fuse, last hitter, tumbling flag, progress) and the spatial hash | `spawn(pos, kind, hp)`, `damage(id, amount, by)`, `target_in_range(pos, range, mode)`; removal returns the death list |
| `Overflow` | Crush labels per cell, the band, each crush's gauge and tier, each tumble's path | `update(changed_cells)` at step 1, `step()` at step 4, `crushes()`, `is_tumbling(id)` |
| `Structures` | Nothing (a facade) | as in v2 |
| `Buildings` | Every building in build order | `can_place`, `build`, `damage(id, amount)`, `is_working(id)`, `act(enemies)` (towers fire, grinders grind), `grind_tumble(id, cell)` |
| `PowerGrid` | Powered flag per building, the grid's cell set | as in v2 |
| `RepairYards` | One drone per yard; each yard's assignment and repair threshold | `assign`, `clear`, `set_threshold(yard_id, percent)`, `is_under_repair(id)`, `step()` |
| `Waves` | Spawn schedule, edges, clump bursts, which spawns are bloaters, Enemies left, wave tail, phase | `bloater_count(wave)`, `enemies_left()`, `in_wave_tail()` |
| `Combos` | Per building: count, tier, timer, best this run | `record(building_id, tick) -> tier`, `expire(tick)`, `remove(building_id)`, `combo(building_id)`, `take_events()` |
| `Blasts` | Nothing between ticks | `resolve(deaths) -> deaths` (adds chained and blast kills, damages structures, erases piles) |
| `RunState` | Gold, base HP, wave number, Kills, game over | `can_afford(cost)`, `pay(deaths, combos, tick)`, `damage_base(amount)` |

### Commands (new and changed)

- `Build(kind, origin)` accepts `grinder`.
- `SetRepairThreshold(yard_id, percent)`, with `percent` one of 25, 50, 75 or 100.
- `SetTargeting(tower_id, mode)`, with `mode` `bloaters_first` or `closest_to_base`.

### Signals out to the view (end of tick)

v2's signals stand, except:

- `combo_changed(tier)` is removed. `combo_events(events)` reports each building's kill pulse, tier-up and break this tick, for the rings.
- `payout(amount, tier)` stays, with the tick's total and the highest tier any kill paid at, for the gold flash.
- `blasts(blasts)` reports each blast's centre this tick, for the blast effect.

Crush gauges, tumbling enemies, combo rings, building HP, drone positions and repair state change every tick, so the view reads them read-only each frame, as the enemy renderer reads the enemy arrays.

## 3. Tick order

The v2 order, with overflow after movement, grinders beside towers, and blasts at removal.

0. Drain commands (builds, assignments, thresholds, targeting, next wave, restart, settings, debug actions). A successful build recomputes power at once.
1. `Piles` lands bodies queued last tick. On the tick after a wave end, `Piles.decay()` and `Routing.start_rebuild()` run next. `Routing` applies the change list (pile level changes, walls broken or erased, buildings built or destroyed, HP bucket changes) as an incremental update, and swaps in the decay rebuild once it is due. `Overflow` relabels its crushes when the change list touches a wall or building.
2. `Waves` spawns, in clump bursts, bloaters among them.
3. Rebuild the spatial hash.
4. Move enemies, as in v2, with bloaters lighting and burning fuses instead of attacking. A bloater whose fuse runs out dies with no killer. Then `Overflow.step()`: track progress in the band, fill and leak each gauge, launch new tumbles, and move every tumbling enemy (a grinder cell crossed hurts it at once).
5. Buildings act, in build order: working towers fire, working grinders hurt every enemy touching them.
6. Drones fly and repair (`RepairYards.step()`).
7. Remove dead enemies, then `Blasts.resolve` the deaths (section 8), then `Combos.expire(tick)` and `RunState.pay` each death in order. Bodies of deaths that leave one go to `Piles.queue_bodies`. Buildings destroyed by a blast leave at once, as at step 4, and lose their combo.
8. `Waves` checks for wave end; on wave end, decay becomes due at step 1 of the next tick, drones fly home, and the phase becomes build phase.

Then the end-of-tick signals are emitted. Removal waits until step 7, so enemy ids and indices are stable for the whole tick.

Every number is a starting value from `docs/design.md`, to be tuned in the QA-and-tuning ticket.

## 5. Map and grid

Sources: [The flared map](https://github.com/vandelay87/pile-up/issues/95), [Map data format](https://github.com/vandelay87/pile-up/issues/12).

- **The v3 map** is `data/maps/v3-flared.json`, ported unchanged from `data/maps/proto-flare-h-west-island.json` at commit e129da6 on `prototype/flared-map`, and `map_path` defaults to it. `v1.json` and `v2-narrow.json` stay in the repo as valid maps, chosen from the debug panel's map dropdown.
  - 112×76 cells, about 3,400 clear. Spawn edges N, E and W, with ragged flared mouths about 51, 33 and 29 cells wide.
  - The north mouth leads into a plaza; two ways run round the central rock, and a trunk runs down to a 4×4 base at (53, 54). The west route is one straight funnel into its junction. A channel about 6 cells wide joins the north and east routes past a rock island of about 7×8 cells. Four small pockets sit beside the chokepoints.
- **No-build cells.** The map format gains one character: `:` is clear ground that enemies walk on but nothing can be built on. Map H marks a margin 6 cells deep along every spawn edge with it. The format's version stays 1, since every older map is still valid. `MapData.is_no_build(cell)` reads it.
- The file format's other rules, validation, grid maths and camera are unchanged. The generator script stays on the prototype branch; the map is data.

## 6. Structures

Unchanged from v2, with grinders joining buildings.

- **One rule.** Walls, buildings and the base are structures. An enemy attacks one only when it is in the way: its route crosses it within 2 steps and it is pressed against it (within `separation_radius + wall_reach` of a structure cell's square), or it is jammed against it (no progress for `jam_seconds` while pressed against it). A bloater never attacks: where a normal enemy would start attacking, it lights its fuse instead (section 8).
- **Damage:** every attacker deals 2 HP/s to the structure cell it attacks. Attackers hold their ground against the crowd behind them.
- **Walls:** 15 HP; at 0 HP a wall drops to a level-3 pile.
- **Buildings:** a tower 60 HP, a grinder 100, a pylon 20, a repair yard 60. At 0 HP a building is destroyed and leaves nothing behind.
- **The base:** 200 HP in `RunState`. No enemy enters it; an enemy pressed against it attacks it. At 0 HP the run ends.
- **Bodies at structures:** an enemy killed at a structure dies in front of it, and its body lands by the normal rule.

## 7. Routing

Unchanged from v2: two integration fields (**sensible** and **direct**) with true shortest-path parents, octile steps with no corner cutting, finite costs for walls and buildings by their time to break, no blocking check, incremental updates that equal a full rebuild exactly, a worker rebuild after decay, route rolls (5% pile, 3% wall or building) and wave-tail push-through (turn-back angle 90°). Grinders count as buildings. An erased pile or wall joins the change list like any pile change.

Tumbling enemies take no part in routing while they tumble (section 10): no route rolls, no push-through, no returns. On landing they walk the sensible field.

## 8. Enemies

Sources: ADR 0001, [The exploding enemy](https://github.com/vandelay87/pile-up/issues/99), [v3 starting numbers](https://github.com/vandelay87/pile-up/issues/114).

### Normal enemies

Storage, the spatial hash, separation (pushes averaged), collision, jam detection, pace, wander and personal space are unchanged from v2. 10 HP (growing ×1.05 a wave), 2 cells/s, bounty 1.

### Kill credit

- `Enemies.damage(id, amount, by)` records `by` (a building id, or `NONE`) as the enemy's last hitter. Towers and grinders pass their id; a blast passes its bloater's credit; debug kills pass `NONE`.
- The death list holds each dead enemy's position, kind, killer (its last hitter) and whether a blast killed it, in removal order.

### The bloater

- **Stats:** 30 HP (×1.05 a wave like any enemy), 1.6 cells/s, bounty 2. Its pace, wander and personal space are as for a normal enemy. It collides and separates at the normal radius; only its drawing is larger.
- **Fuse:** where a normal enemy would start attacking a structure in its way, a bloater lights a 1 s fuse (60 ticks) and holds its ground like an attacker, but deals no damage. When the fuse runs out, its HP drops to 0 with no killer (`NONE`), so it is removed and blows up at step 7. Killing it during the fuse blows it up there, credited to its killer.
- **Tumbling:** a bloater with a lit fuse isn't an attacker, so `Overflow` may pick it to tumble. Starting a tumble puts its fuse out; it lights again at the next structure in its way after it lands.
- **No body:** a bloater never adds to a pile.

### Blasts

`Blasts.resolve(deaths)` runs once at step 7, after removal:

1. Each bloater in the death list, in order, blows up at its death position. Every living enemy whose position is within 2 cells of that centre dies, as a blast kill credited to the bloater's killer. Blast kills are taken from the spatial hash with its usual margin, checking exact positions, and removed at once. A blast kill that is a bloater blows up in turn, with the same credit, so chains resolve breadth-first and every bloater blows up once.
2. Every building with a cell centre within 2 cells of a blast takes 30 damage once per blast; so does the base when any base cell centre is. Damage applies after every kill in the chain is credited, so a building destroyed by a blast it caused still keeps that blast's kills.
3. Every pile or wall with its cell centre within 2 cells of a blast is erased (`Piles.erase`), leaving a clear cell. Erased cells join the change list.
4. The hard edge: inside takes the full effect, outside nothing.
5. Bodies: a blast kill leaves no body, and a bloater never does. Every other death queues its body as normal.

The blast list goes to the view through `blasts(blasts)`.

### Movement (step 4)

As in v2 (flow field, heading offset and wander, pace and pile slow, separation and personal space, collision, route rolls, returns and push-through, structure attacks), with the fuse in place of an attack for a bloater, progress tracked inside the crush band (section 10), and tumbling enemies skipped: they don't walk, collide, separate, attack or roll, and others don't separate from them.

## 9. Piles and walls

Unchanged from v2: five levels (15/30/45/60% slow, then a 15 HP wall), bodies landing on the cell their enemy died on or the nearest valid cell from the death position, a broken wall dropping to a level-3 pile, and decay on a roll at wave end (50% for levels 1–4, 25% for walls, one level at most, walls keeping their damage).

- **Erasing.** `Piles.erase(cell)` clears a pile or wall of any level at once, mid-wave, and joins the change list. Only a blast erases.
- **Tumbling deaths.** An enemy killed mid-tumble may die over a wall or building; its body goes to the nearest valid cell from its death position, so it lands on whichever side is nearer. No new rule.

## 10. Pressure and overflow

Sources: [How crowd sims measure density and pressure](https://github.com/vandelay87/pile-up/issues/93), [Dense hordes overflow piles and walls](https://github.com/vandelay87/pile-up/issues/91), [Overflow prototype](https://github.com/vandelay87/pile-up/issues/94). The prototype is `src/sim/overflow/overflow.gd` and `src/view/overflow_view.gd` on `prototype/overflow`; the build ports its rules test-first, without its debug alternatives, and relabels on change instead of on a timer.

### Crushes

- **Barriers.** Every barrier (a connected stretch of wall and building cells, 8-way) gets a label. Piles at levels 1–4, rock and the base are never part of a barrier. `Overflow` relabels when the step-1 change list turns a cell into, or out of, a wall or building; a relabelled barrier keeps the gauge of the old barrier it overlaps most, ties to the lower old label, so a gauge survives a wall forming or a building going up beside it. Each old gauge goes to one barrier: when a barrier splits, the part that overlaps it most keeps it.
- **The band:** every clear or pile cell within 3 steps of a barrier (8-way, walking only through cells that aren't rock or structure) is in that barrier's band. A cell in two bands belongs to the nearer barrier, ties to the lower label.
- **Progress.** For each walking enemy in a band, `Enemies` tracks its progress: the drop in its route field's value this tick as a share of a full step at its pace, smoothed with a fixed exponential average. Outside a band, progress is reset to 1.
- **Stalled:** an enemy in a band whose progress is below 25%. Attackers and fusing bloaters count. Tumbling enemies don't.
- **The front rank** of a barrier: stalled enemies within an attacker's reach of one of its cells.

### The gauge

Per barrier, each tick (dt = 1/60 s):

- Fill 0.5 × stalled enemies per second, minus a leak of 5 per second, clamped between 0 and 120.
- The crush is **active** once the gauge passes 10 and stays active until it falls below 4.
- **Tier** while active: trickle from 20, stream from 50, surge from 90; none below 20.
- The gauge is drawn above the mean position of the crush's stalled enemies.
- A barrier with an empty, inactive gauge is dropped from `crushes()`.

### Launching tumbles

- While a crush has a tier, it banks its tier's rate (0.5, 3 or 15 enemies/s) as credit each tick. Each whole credit launches one tumble.
- **Who goes:** front-rank enemies that aren't attacking, picked at random along the front with the overflow RNG, so overflow comes over as a broad front. Attackers are picked only when every enemy in the front rank is attacking. An enemy whose tumble can't be planned is skipped.
- **Relief:** each launched tumble takes 2 off the gauge.

### Planning a tumble

- **Straight over:** of the wall and building cells the enemy is touching, take the one whose direction from the enemy (in one of 8 directions) faces most nearly towards the base by the direct field. The path runs from the enemy's position straight along that direction, over that cell and any wall or building cells beyond it in line, to the first cell that is clear or a pile, has fewer than 6 enemies in its spatial-hash bucket, and isn't rock or the base. There is no limit on how far a tumble crosses.
- **Fallback:** if nothing the enemy touches faces forwards, or the straight line hits rock or the map's edge first, it follows the direct field's parent chain over the obstacle to the first such cell instead.
- **Reaching the base:** if the path reaches a base cell before a free cell, the tumble ends on the free cell beside the base nearest where the path reached it, and the enemy attacks the base from there.

### Tumbling

- A tumbling enemy moves along its path at 180% of its walking speed (pace included), ignoring piles' slow, collision, separation and structures. It doesn't attack, roll, light a fuse or count towards any crush.
- It can be targeted, shot and killed like any enemy. Towers' targeting needs no change; closest to the base already favours tumblers.
- Each time it enters a grinder's cell, that grinder hurts it at once by one second's worth of its damage (section 13).
- On reaching the path's end it lands: walking resumes on the sensible field, with its route-roll and jam state reset.
- `Overflow.is_tumbling(id)` and the path are read by the view, which draws a tumbling enemy raised.

### What overflow changes

Nothing it crosses: no wall loses a level and no building is damaged by a tumble. Route rolls and wave-tail push-through stay as they are, alongside overflow. Blasts need no rule: their kills shrink the crush, and an erased wall is a hole, not an overflow. With `overflow.enabled` off, gauges, launches and tumbles all stop (tumbles in flight finish).

## 11. Buildings, power and under repair

Sources: [Power grid](https://github.com/vandelay87/pile-up/issues/52), [Buildings being repaired can't function](https://github.com/vandelay87/pile-up/issues/90).

### Buildings

| Kind | Footprint | Cost | HP | Power area | Hotkey |
|---|---|---|---|---|---|
| Tower | 2×2 | 80 | 60 | 4 | T |
| Grinder | 2×2 | 60 | 100 | 2 | G |
| Pylon | 1×1 | 20 | 20 | 10 | P |
| Repair yard | 2×2 | 80 | 60 | 4 | R |
| Base (not a building) | 4×4 | – | 200 | 10 | – |

### Power

Unchanged from v2: square power areas from the footprint's edge (Chebyshev), powered through overlaps outwards from the always-powered base, recomputed whenever the set of buildings changes. An unpowered building stops working but stays a structure.

### Under repair

- A building is **under repair** while any drone is in `REPAIRING` on it; the flight there doesn't count. `RepairYards.is_under_repair(id)`.
- `Buildings.is_working(id)` = powered, and not under repair unless it is a pylon. A pylon under repair keeps powering, so a repair never changes the power grid.
- A building that isn't working: a tower holds fire and keeps its cooldown; a grinder hurts nothing, touching or tumbling; a repair yard's drone flies home and stops, as when unpowered.
- A building under repair still blocks, is attacked, stays part of its barrier and is tumbled over.
- Drones step at step 6, after buildings act at step 5, so a repair that starts on a tick stops the building from the next tick.

### Placement (step 0)

`Buildings.can_place(kind, origin)`: every footprint cell is in bounds, not a no-build cell, on the power grid, and clear (no rock, base, building or pile) → `RunState.can_afford(cost)`. Rejections: "off the map", "too close to a spawn edge", "off the power grid", "occupied" or "not enough gold". Building is allowed during waves and in the build phase. No selling or demolishing.

## 12. Towers

Unchanged from v2 except for targeting: 5 damage, 3.5 shots/s, range 8 cells from the footprint's centre, instant hits, firing in build order, cooldown in ticks, ready on the tick it is built. Only working towers fire. Each tower counts its kills this run.

- **Targeting** is per tower, set by `SetTargeting`:
  - `bloaters_first` (the default for a new tower): the bloater in range closest to the base (lowest sensible-field value, ties to the lowest id), else the enemy in range closest to the base. Tumbling bloaters count.
  - `closest_to_base`: v2's rule.
- If popping tumbling bloaters plays badly, the fallback recorded for QA is that `bloaters_first` skips tumbling bloaters.

## 13. Grinders

Sources: [A building that hurts on contact](https://github.com/vandelay87/pile-up/issues/98).

- A building under every rule (section 11): placed on the grid, powered, attacked, repaired, part of a barrier, destroyed leaving nothing.
- **Touching:** an enemy is touching a grinder when it is within an attacker's reach (`separation_radius + wall_reach`) of one of its cells' squares, the same test as "pressed against". Walkers, attackers, fusing bloaters and the crush all count; tumbling enemies don't (they take per-cell damage instead).
- **Contact damage (step 5):** each working grinder, in build order, deals 3 HP/s (3/60 a tick) to every living enemy touching it, found through the spatial hash. An enemy touching two grinders takes both. The grinder that brings an enemy to 0 HP is its killer.
- **Tumbling:** each time a tumbling enemy enters a cell of a working grinder, it takes 3 damage at once (one second's worth) from that grinder. A 2×2 grinder crossed straight is 2 cells, so 6 damage.
- **Combos:** its kills build its own combo, tumbling kills included.
- **Bodies** land by the normal rule, so piles build up against it.
- Each grinder counts its kills this run and the enemies touching it this tick, for the details.

## 14. Repair yards

Sources: [A building that heals](https://github.com/vandelay87/pile-up/issues/67), [Buildings being repaired can't function](https://github.com/vandelay87/pile-up/issues/90).

Unchanged from v2 (one drone per yard; `HOME → OUTBOUND → REPAIRING → RETURNING`; straight flight at 8 cells/s; 5 HP/s until full; drones on one building add their rates; picking only when home or when its target is destroyed, only during a wave while the yard works; drones step in build order), except:

- **Repair threshold.** Each yard has a threshold of 25, 50, 75 or 100% of max HP, 50% when built, changed by `SetRepairThreshold`. A candidate is a building in the yard's repair area, other than the yard, whose HP is below that share of its max HP (at 100%, any damage). The assignment counts only while it is below the threshold too. A drone that has started repairs to full.
- **Picking:** assignment first when it is below the threshold; else auto among candidates, nearest the yard, then lowest HP, then lowest id, preferring one no other drone is targeting.
- **Working:** a yard that isn't working (unpowered or under repair) sends its drone home, as v2 did for unpowered.
- Each yard counts the HP it has repaired this run.

## 15. Waves, run state and combos

Sources: [Bloaters in waves](https://github.com/vandelay87/pile-up/issues/110), [Combo rework: per-building combos](https://github.com/vandelay87/pile-up/issues/97), [v3 starting numbers](https://github.com/vandelay87/pile-up/issues/114).

### Waves

- Phases, "next wave", HP growth ×1.05 and spawn edges (1 or 2 of the map's edges) as in v2. Wave size `round(20 × 1.25^(n−1))`: about 149 at wave 10, 455 at wave 15 and 1,390 at wave 20.
- **Clump spawning:** bursts of 16, each on a seeded random spawn cell along the wave's edges, averaging 10 per second.
- **Bloaters:** from wave 5, `bloater_count(n) = max(1, round(share(n) × size(n)))` with `share(n) = min(5%, 2% + 0.3% × (n − 5))`: 1 at wave 5, 5 at wave 10, 23 at wave 15, 69 at wave 20. Before the first bloater wave the count is 0. At wave start, `Waves` picks which spawn slots (0 to size − 1) are bloaters, without replacement, with its seeded RNG, so they land at random among the bursts. Bloaters take normal enemies' places; the wave size is unchanged.
- **Enemies left** = wave size − kills this wave, bloaters included. In the build phase it reports the next wave's size, and `bloater_count` the next wave's bloaters.
- **Wave tail:** Enemies left ≤ 10 + 2 × the wave number. **Wave end:** every enemy has spawned and none remain alive.

### Run state

- Base HP 200 and gold 200 at the start of a run; `damage_base` lowers base HP; at 0 the run ends and `game_over` is emitted. After it, the simulation accepts only a restart.
- **Kills** counts every death in the run, bloaters, blast kills and fuse pops included.
- The global combo is removed.

### Combos

- **Per building.** `Combos` keeps, for every building with a combo: its count, its tier, the tick its timer runs out and its best tier this run. Any building that lands a kill can hold one (towers and grinders).
- **A kill** credited to a building adds 1 to its count, sets its tier (×1 below 10, ×2 from 10, ×3 from 25, capped at ×3) and restarts its timer (2 s, 120 ticks). The kill that crosses a threshold already counts at the new tier.
- **A break:** at step 7, before paying, every combo whose timer has run out resets to count 0, tier ×1.
- A destroyed building's combo is removed with it; a rebuild starts at ×1. Damage to a building or the base never breaks a combo. A building under repair can't kill, so its timer simply runs out.
- **Pay:** each death in order pays its kind's bounty (1, or 2 for a bloater) × its killer's tier after counting that kill. A death with no killer, or whose killer was destroyed this tick, pays ×1 and feeds no combo. A bloater that blew itself up (fuse, with no killer) pays no bounty of its own; its blast kills pay ×1.
- **Events:** each kill pulse, tier-up and break, per building, go into `Combos.take_events()` for `combo_events`. `payout(amount, tier)` fires once per tick when any kill paid above ×1.

## 16. View

The v2 view stands: plain coloured shapes from one committed atlas, one y-sorted world, pooled enemy canvas items, pile lift, hit flash, tracers, drones, pan and zoom, UI scaling. v3 adds:

- **Atlas:** grinder, bloater and a blast ring, drawn by `tools/make_atlas.gd`.
- **No-build margin:** tinted (as on the prototype, red) while a building is being placed.
- **Bloaters** drawn in their own colour at 1.5× size; while its fuse burns, a bloater pulses faster and faster. A blast draws a short ring of its radius.
- **Tumbling enemies** drawn raised, from `Overflow`'s tumble state, ported from `prototype/overflow`.
- **Pressure gauge:** above each crush's stalled enemies, from `Overflow.crushes()` each frame, in segments for the three tiers in yellow, orange and red, with the tier's name on it. Ported from `src/view/overflow_view.gd` on `prototype/overflow`.
- **Combo ring** above each building with a combo, hidden at ×1: its tier in the middle, an outer arc filling towards the next tier (full at the cap), an inner arc for the timer, red when nearly out. A kill pulses it, a tier-up sends a ring outwards as the number swells, a break scatters red arc fragments as the number drops away. A steady on-screen size at any zoom, in shades of gold per tier. Ported from `_draw_ring` in `src/view/prototype_combo_view.gd` on `prototype/combo`, with v3's numbers.
- **Bottom HUD**, the StarCraft-style console, ported from variant A in `src/view/hud/prototype_bottom_hud.gd` on `prototype/bottom-hud`: one full-width bar about 150 UI units high, built in `UiRoot` units so v2's scaling holds and six-digit numbers fit at 3024×1890.
  - **Status, left:** Gold (flashing on a multiplied payout), Base HP, Wave, Enemies left and Kills, as a two-column table. In the build phase Enemies left reads like "120 enemies · 3 bloaters", the bloater part hidden at 0.
  - **Details, middle:** always there, "Nothing selected" when empty. This replaces the floating panel. A portrait placeholder sits on its left.
  - **Command card, right:** square buttons for Tower, Grinder, Pylon and Repair yard, each with its cost and hotkey, and Next wave, in one grid with empty slots kept.
  - Toasts sit just above the bar. Nothing sits at the top right.
- **Details for the selection** (clicking a building or the base selects it; empty ground or **Esc** clears it; a destroyed selection clears itself). The selection shows its range as in v2. The details show HP and max HP and a one-word **status**: Unpowered, else Under repair, else Firing or Idle (tower), Grinding or Idle (grinder), Repairing or Idle (repair yard), Powering (pylon); the base has none. Then:
  - a tower: damage, shots/s, range, its kills this run, and its targeting toggle (Bloaters first / Closest to base);
  - a grinder: damage per second, enemies touching it now, its kills this run;
  - a repair yard: repair rate, auto or its assignment (Assign and Clear), its threshold (a 25/50/75/100% control), HP repaired this run;
  - a pylon: its power area;
  - a building with a combo (a tower or a grinder): its ring drawn large, with tier and count, the next tier's threshold, time left on its timer, and its best combo this run.
- **Removed:** v2's global combo readout.

## 18. Testing, CI and performance

Sources: [Testing, CI and performance checks](https://github.com/vandelay87/pile-up/issues/10).

### The test seam

- **The Simulation is the seam**, as in v2: build a `Simulation` on a tiny inline map (`TestMaps.from_rows`, which learns `:`) with fixed settings and seed, queue commands, run ticks, and assert on public state and end-of-tick signals. Tests set up a situation, as a player or the debug panel could, and check what comes out.
- New public state to assert on: each crush's gauge, tier and active flag; which enemies are tumbling and where they land; per-building combos (count, tier, best); each death's killer; gold paid; piles erased; building and base HP after a blast; whether a building is working; drones' choices against a threshold; the next wave's bloater count and the kinds spawned.
- **Kept seams:** the routing exactness test stays at `Routing`; `bench_sim` and the local frame benchmark stay the performance seam.
- v2 tests the v3 rules change (the global combo, payout, the wave size, tower targeting, drone picking) are rewritten by the ticket that changes the rule.
- Each build ticket's acceptance criteria name the tests it adds, written test-first. Rendering, input and UI (the bottom HUD, rings, gauges, tints, tumbling drawn raised, the bloater's pulse and the blast) have no automated tests; the human checks them in playtests.

### CI and performance

- CI is unchanged: `lint`, `test`, `sim-budget` and `export`, all required on every PR.
- `bench_sim.gd` grows to include a crush overflowing at surge on the v3 map, grinders under a crush, and a bloater chain erasing a wall, alongside v2's cases. Its limit changes only in a PR that explains why.
- PRs that touch the enemy module, flow fields, overflow, blasts, grinders, the tick driver, power, drones or drawing paste the local M5 table in the PR's Performance section.
